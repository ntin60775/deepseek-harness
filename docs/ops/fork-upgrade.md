# Обновление форка DSH до нового апстрима

## Когда

Любой перенос `upstream/master` в форк: плановый мерж релиза, срочный фикс или догоняющий мерж после серии локальных коммитов. Мерж без этой процедуры считается незавершённым, даже если git-конфликты разрешены и сборка прошла.

## Гейты

1. **Чистое дерево.** `git status --porcelain` пуст, stash пуст; иначе ритуал падает на preflight. Локальную работу коммитить или прятать до начала.
2. **Аудит форка.** `pnpm run fork:upgrade-audit --strict`: диапазон от тега в `packages/fork/upstream-base.json` до `upstream/master`, новые и изменённые upgrade-guide'ы, пересечение файлов «менял апстрим / менял форк», слоты форк-плагинов и строки профилей. `MISSING`-слот или нерезолвимый пакет/субпас — стоп.
3. **Чтение гайдов.** Каждый новый `docs/upgrade-guide/**/guide.md` читается до адаптации; названное в нём удаление слота, тула, пакета, экспорта или дефолта — задача в этом же мерже, а не заметка.
4. **Адаптация поверхностей.** `packages/fork/*`, внешние плагины из `DSH_FORK_PLUGIN_DIRS` (по умолчанию `~/home/dev/dsh-plugins`) и патчи `~/.dsh/profiles/*/cordis.patch.yml`. Внешний плагин пересобирается после правки исходников.
5. **Классификатор UI темы.** `node <theme>/verify/classify.mjs --checkout <чекаут> --strict`: `MISSING` — мёртвое правило темы или расхождение таблицы и `tui.css`; `NEW` — неклассифицированный вид узла, хук или слот. Новые поверхности классифицируются в `verify/surfaces.json`, мёртвые снимаются.
6. **Ритуал.** `scripts/fork-merge-ritual.sh` выполняет гейты 1–5 в одном прогоне, затем build, перегенерацию каталогов, `typecheck`, `constraints`, `test:docs`, `test:gui`, `test:snapshot`, запись базы и коммит поверхностей. Пуш — только после зелёного прогона и отдельного решения оператора.

## Живая проверка UI

Автоматика ловит только записанные carriers: слоты, `data-*`-хуки, виды узлов чата. Обычная кнопка без хука при переезде остаётся невидимой, поэтому после мержа нужен проход по живому UI: шапка сеанса и тоггл панели сеанса, composer dock, страница Plugins, переопределённые Settings и все экраны, которые рисуют форк-плагины.

Основной хост `:3080` из сессии не рестартится: агент живёт внутри него. Проверка идёт вторым инстансом: `dsh web --port 3081 --no-open` с отдельным `DSH_HOME` и тем же профилем (пакеты разрешаются по абсолютным путям из `~/.dsh/profiles/<name>/package.json`).

Хост, поднятый до сборки, отдаёт старый список client-rows: новой строки из бандла (например `ui-session-panel`) в нём нет, даже если страница уже показывает новую версию. Признак — время старта процесса раньше времени сборки; лечение — рестарт хоста (решение оператора) или проверка на втором инстансе.

Строка патча профиля, которая добавляет новый плагин, пишется внутри `insert:`; top-level `- id:` без такой записи в бандле молча пропускается с предупреждением `patch: entry "x" not found`, и плагин не загружается.

## База и провал

`packages/fork/upstream-base.json` хранит тег последнего влитого апстрима; sha в файле запрещён гейтом `verify-repository-references`, поэтому база именуется тегом, а не коммитом.

Ритуал записывает базу только после всех зелёных гейтов: упавший прогон оставляет старую, и следующий аудит проверяет тот же диапазон заново. Ручной мерж без ритуала обязан вызвать `pnpm run fork:upgrade-audit --record-base` сам.

Прерванный мерж: `git merge --abort` возвращает дерево к базе, если конфликты ещё не закоммичены; после коммита мержа откат — отдельное решение оператора через `git revert -m 1 <merge>`, потому что история форка линейна по первой линии.
